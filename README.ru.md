# TeamWork

> **Раскрытие использования ИИ:** проект создан при помощи **OpenAI Codex (GPT-5)**. Владелец проекта проверил и принял реализацию и документацию.

TeamWork периодически получает задачи Jira через встроенный read-only MCP-сервер, группирует их, создаёт Markdown-документ и показывает его в веб-интерфейсе, похожем на редактор.

## Возможности

- Встроенный read-only Jira MCP sidecar на официальном MCP SDK.
- Браузерная авторизация Atlassian OAuth 2.1 через официальный Atlassian Rovo MCP с шифрованием токенов.
- Получение и выбор нескольких Jira-проектов с опросом по расписанию и отдельным документом для каждого выбранного проекта.
- Вкладки выбранных проектов с подвкладками Backlog и Sprints и сохраняемый переключатель русского/английского интерфейса.
- Настраиваемая иерархия: Goal → тема → активный спринт → будущий спринт → бэклог.
- Периодическая и ручная синхронизация.
- Структура документа, поиск, scroll-spy и вложенное сворачивание разделов.
- Отдельная вкладка «Спринты» с иерархией размещение → Goal → направление и порядком активный, будущий, бэклог.
- Значки типов и статусы задач в заголовках.
- Копирование задачи одним кликом в rich text с сохранением Jira-ссылки для Confluence, OneNote и текстовых редакторов.
- Локальные комментарии под заголовками задач и панель управления ими.
- Локальные метки задач и группировка по всем меткам с приоритетом над themes.
- Каталог локальных меток с выбором существующих, счётчиками использования и подтверждаемым глобальным удалением.
- Независимое хранение комментариев и удаление записей исчезнувших задач.
- Структурированные JSONL-логи и просмотр журнала в интерфейсе.

## Требования

- Docker с Compose; рекомендуется Docker Desktop 4.62 или новее.
- Учётная запись Atlassian с доступом к сервису Atlassian Rovo MCP.
- Node.js 22+ для локальных проверок вне Docker.

## Настройка и запуск

```bash
cp grouping.config.example.json grouping.config.json
```

В `grouping.config.json` обязательны только расписание и логирование. Ключи проектов и базовый адрес Jira в этой конфигурации не задаются. Опрашиваемые проекты выбираются на вкладке **Проекты**, а необязательный адрес Jira — на вкладке **Интеграция**. Имя и путь документа вычисляются отдельно для каждого проекта. Правила независимы и хранятся в `data/workspace.json` под ключом `groupings.<PROJECT_KEY>`; по умолчанию группировка Backlog отсутствует.

### Авторизация Jira MCP

Запустите TeamWork:

```bash
./start.sh
```

Во вкладке **Интеграция** нажмите **Подключить Atlassian**. TeamWork откроет официальный экран согласия Atlassian и выполнит OAuth 2.1 через PKCE и dynamic client registration. Client ID, Client Secret, приложение в developer console и API token не требуются. Зашифрованная OAuth-сессия и её ключ вместе сохраняются в приватном Docker volume, поэтому рестарт, пересборка, перенос проекта и обычное пересоздание контейнера не требуют нового входа. Локальный sidecar предоставляет только read-only операции TeamWork и не публикует порт на host; официальный Atlassian Rovo MCP upstream запрашивается только с Jira read scopes.

Доступные MCP tools: `jira_list_sites`, `jira_list_projects`, `jira_export_snapshot`, `jira_search_issues`, `jira_get_issue`. Встроенный сервер является единственным поддерживаемым MCP-провайдером. Cloud ID сайта определяется по подключённой учётной записи Atlassian и сохраняется как внутреннее состояние workspace.

После запуска откройте [http://localhost:8080](http://localhost:8080).

Для создания или пересоздания контейнеров всегда используйте `./start.sh`. Прямой `docker compose up` намеренно блокируется: он не может передать временный внутренний MCP-токен и ключ шифрования.

### Сетевой доступ и авторизация

По умолчанию Compose публикует сервис только на `127.0.0.1`. Для доступа из доверенной сети явно включите Basic Auth и измените адрес:

```bash
APP_BIND_ADDRESS=0.0.0.0 \
APP_AUTH_USER=owner \
APP_AUTH_PASSWORD='длинный-случайный-пароль' \
./start.sh
```

Не публикуйте сервис в интернете без HTTPS-прокси. Пароль передаётся только при запуске и не должен попадать в Git.

## Локальные данные

Документ, комментарии, логи и PID-файлы находятся в `data/` и не публикуются. Комментарии не отправляются в Jira и не добавляются в Markdown.

Для проекта создаются отдельные документы `<PROJECT>-backlog.md` и `<PROJECT>-sprints.md`. Backlog никогда не группируется по спринтам: без явных правил это общий список, а при наличии правил применяются только темы данного проекта и локальные метки. Sprints остаётся представлением по размещению. Кнопка **Анализировать** выполняет семантическую классификацию сохранённого снимка проекта. Ручные правила сохраняются, а правила с `source: "analyzer"` при каждом запуске строятся заново по актуальным задачам.

### Провайдеры семантического анализатора

По умолчанию анализатор использует встроенный сервис Ollama (`qwen2.5:3b`). Перед первым анализом загрузите модель в постоянный volume: `./start.sh --pull-model`. На вкладке **Интеграция** можно подключить OpenAI-совместимый внешний endpoint, модель и API key. Само подключение не активирует провайдер: Ollama или External LLM выбираются отдельным переключателем. Внешний ключ шифруется AES-256-GCM в приватном Docker volume `llm-secrets` и не записывается в workspace или grouping-файлы. LLM классифицирует смысл задачи и возвращает описание, примеры и точный список задач группы вместо keyword regex.

### Метки задач и приоритет группировки

Откройте задачу кнопкой `💬` или нажатием на существующую метку. В панели задачи можно добавить до десяти локальных меток, выбрав существующую из каталога или введя новое имя. Кнопка `×` снимает метку только с текущей задачи. Каталог показывает количество использований и позволяет после подтверждения удалить метку у всех задач. При синхронизации локальные метки полностью перекрывают классификацию по themes: задача отображается во всех соответствующих группах `Метка: <метка>`. Задачи без локальных меток классифицируются по взвешенным совпадениям в заголовке, Jira labels, components и описании. Веса задаются через `grouping.sourceWeights`, а порядок themes разрешает только ситуации с равным количеством баллов. Метки хранятся в `data/labels.json`, не отправляются в Jira и удаляются, когда задача исчезает из документа.

`Goal` всегда остаётся верхним уровнем. Задачи без заполненного Jira Goal находятся в группе `Goal: <emptyGoalLabel>`. Внутри направления расположение всегда сортируется так: активный спринт, будущий спринт, бэклог.

## Разработка и безопасность

```bash
npm ci
npm run check
docker compose build
```

В GitHub Actions включены синтаксические и функциональные тесты, `npm audit`, CodeQL и dependency review. Контейнер работает без root, с read-only root filesystem, сброшенными capabilities, `no-new-privileges` и healthcheck. Пути документов ограничены каталогом `data/`. Dependabot, secret scanning, push protection, приватные отчёты об уязвимостях и автоматические security updates включены в репозитории. Подробности — в [SECURITY.md](SECURITY.md).
